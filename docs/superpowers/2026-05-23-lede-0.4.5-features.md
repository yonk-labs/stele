# Notes — lede v0.4.5 features (and what they mean for stele)

Date: 2026-05-23
Source: lede v0.4.5 handoff (https://github.com/yonk-labs/lede/releases/tag/v0.4.5)
PyPI: `lede==0.4.5`, `lede-spacy==0.4.5`

## Headline

`readable_report()` / `lede --mode report` now produce **two distinct output
surfaces** from the same extraction:

| Surface | Methods | Shape | Use for |
|---|---|---|---|
| **Human** | `.to_markdown()`, `.to_text()` | compact, low-token | what the LLM/reader sees |
| **Machine** | `.to_json()`, `.to_dict()` | full-fidelity payload | ingest, metadata promotion, SQL columns, FTS, embedding enrichment |

This is the key split: the human surface is the cheap context we send a model;
the JSON surface is structured data for the *ingest/retrieval* side. They are
not the same content at different verbosities — JSON carries machine-only fields
(promotion paths, evidence payloads, `search_text`) the human surface omits.

New exported types: `ReadableReport`, `ReportAttribute`, `FactRecord`,
`PromotionCandidate`.

## The JSON data model (new in 0.4.x line, formalized in 0.4.5)

- **`attributes`** — normalized key/value metadata pulled from obvious document
  structure (`**Term:** 2023` → `{"term": {"value": "2023", "type": "year",
  "source": "header_kv", "evidence": "...", "confidence": 0.99}}`).
- **`fact_records`** — typed S-P-O records (`{subject, predicate, object,
  fact_type, evidence, confidence}`); includes numeric facts and, with spaCy,
  entity-number facts.
- **`promotion_candidates`** — stable JSON paths an ingest system can promote to
  first-class **filterable metadata columns**
  (`lede_report.attributes.term.value`, `promote: true`).
- **`search_text`** — flattened summary/facts/attributes/entities for **FTS or
  embedding enrichment**: index this when retrieval should search over extracted
  facts/details, not just original content.

spaCy stays opt-in (`backend="spacy"`); plain report does not add spaCy
entities/facts. spaCy adds `spacy_metadata`, `spacy_facts`, `spacy_phrases`
(JSON) and entity/noun-phrase/entity-fact-link sections (human).

## What this changes for stele

### 1. digest_search summarizer (sibling spec) — bump 0.4.4 → 0.4.5, no design change
The summarizer still consumes the **human** surface
(`readable_report(...).to_markdown()`) — explicitly "compact, low-token," which
is exactly what we want for the recall `context`. So the digest_search design
holds; only the version pin moves to `>=0.4.5,<0.5`.

### 2. Soft metadata filtering gets a real substrate
The original "extract metadata from the prompt → soft-filter" idea was thin
because stele chunks only carry `namespace`/`session_id`. v0.4.5's `attributes`
+ `promotion_candidates` give a *document-side* structured-metadata source:
ingest-time, store `lede_report` JSON on the chunk and promote
`attributes.*.value` into filterable fields. Soft-filter then boosts on real
extracted attributes (term, docket, citation), not just keyword overlap. This is
a stronger version of the feature than slice-1 query-rewrite — likely belongs
with **slice 2** (chunkshop native search / FTS), where the columns can be
queried server-side.

### 3. `search_text` ↔ slice-2 FTS / embedding enrichment
`search_text` is purpose-built for the slice-2 direction: index/embed the
flattened facts+attributes instead of (or alongside) raw chunk text, so exact
terms the embedder misses (names, IDs, citations) become retrievable. Pairs
directly with chunkshop 0.5.0 FTS.

### 4. Pre-staging (the precompute idea) now has a format
The "background-process summaries + fact extraction and store them" follow-up
has a concrete artifact: store `readable_report(...).to_json()` at
`metadata.lede_report` at ingest, promote attribute paths to columns, embed
`search_text`. Precompute once, reuse on every recall.

### 5. Grounding benchmark — SCOTUS lane gets a wrinkle worth testing
lede's 0.4.5 SCOTUS guidance says **deterministic** questions ("which terms
mention Justice Jackson?") should be answered by **filtering promoted metadata
first**, using RAG only to explain — not semantic retrieval alone. Implication
for the grounding spec's authored SCOTUS gold: deliberately include a class of
**attribute/deterministic** questions (term, docket, citation, justice) so the
benchmark can show where metadata-filter beats both raw-chunks and digest. This
may justify an extra **`metadata_filter` lane** in a later round — noted, not
added to the core matrix yet.

Recommended ingest pattern from the handoff (for when we wire enrichment):
```
metadata.lede_report                      # store full to_json()
metadata.lede_report.attributes.term.value        # promote → SQL column
metadata.lede_report.attributes.docket_number.value
metadata.lede_report.search_text          # index/embed for enriched retrieval
```

## Action items (not yet applied to the specs)

- **digest_search spec:** bump dependency pin `lede >=0.4.4` → `>=0.4.5,<0.5`.
  No other change (human surface unchanged).
- **grounding spec:** when authoring SCOTUS gold (~40 pairs), include a subset
  of deterministic attribute questions; flag a possible future `metadata_filter`
  lane.
- **slice 2 (future):** design ingest enrichment around `to_json()` —
  `attributes`/`promotion_candidates` → filterable columns, `search_text` →
  FTS/embedding. This is the home for the stronger soft-metadata-filter.

## Key rule (verbatim from the handoff)

Use Markdown/text for compact readable output. Use JSON for agents, ingest,
metadata promotion, FTS, SQL, and evaluation.
